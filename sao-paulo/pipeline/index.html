Engineering notes · from public data to a drivable city

The
pipeline

Sem Destino is not modelled, it is manufactured. Every 500 m square of São Paulo goes through the same assembly line: fetched, built, repaired, checked, named, cleaned, verified and shipped, by scripts running on a laptop, rented cloud machines and a rented GPU. This page walks the whole line, stage by stage, and lists every trick we found that makes it fast and cheap enough for one person.

The unit of work

Everything is a tile

The world is cut into 500 × 500 m tiles, each its own Blender file in a shared world frame (metres from MASP, x east, y north). A tile can be built, repaired, checked, uploaded or rebuilt on its own, on any machine, in any order. That one decision is what makes everything else on this page possible: parallel work, cheap restarts after a crash, cloud machines that can disappear at any moment, and a progress map where every square has a state.

01
Stage one

Sources

Running

What goes in

  1. GeoSampa (Prefeitura de São Paulo): 3D building footprints with heights, lots, sidewalks, street trees, lighting, the official street register with house-number ranges, districts, terrain.
  2. OpenStreetMap: roads and their classes, one-ways and lanes, land use, shops and amenities, rail, landmarks, and everything outside the São Paulo municipality (Guarulhos, the ABC cities, Osasco), where GeoSampa doesn't reach.
  3. Terrain: a 2 m elevation model per tile.
  4. Street-level photos: 2.3 million indexed by tile with camera position and heading, used only as measurement reference, never as textures.
  5. Published facts for the hand-built parts: station depths, runway dimensions, bridge geometry.

Efficiency

  • Offline map extract instead of live queries. Public OSM query servers regularly time out or wait 100+ s per tile. One regional extract, cut to the São Paulo box, is downloaded once per machine and read locally.
  • Fetch once, reuse everywhere. Terrain and source data are cached per tile, so re-running a later stage never re-downloads.
  • Photos indexed as metadata first. Positions and headings for millions of images take minutes; pixels are fetched only for the buildings that need them.
02
Stage two

Tile build

Running · Rodoanel ring 1

Three steps per tile

  1. Build (~80 s): terrain mesh, roads cut into it, sidewalks and curbs, buildings extruded from footprints with parametric façades (family, colour, glazing, floor height, bay width), trees, poles, bins and street furniture placed from survey layers.
  2. Detail (~55 s): residential refinement: lots, front walls, gates, roofs and water tanks, driveways, yard paving. Near-empty tiles (forest, reservoir) skip it automatically.
  3. Finalize (~10 s): materials unified, a lightweight proxy model built for distant views, a top-down render for the map and the website.

Efficiency

  • Parallelism set by memory, not cores. Build peaks near 3 GB and detail near 5 GB, so a guard reads free RAM every minute and raises or lowers how many tiles run at once. CPU is rarely the limit.
  • Build in rings outward. New tiles are ordered by distance from what is already built, so the map is always one connected piece, never islands.
  • Failures are isolated. A crash costs one tile, gets logged with its error, and is rebuilt later in a targeted fix run (the north block: 45 failures, all 45 rebuilt in one 30-minute pass).
03
Stage three

Repair chain

Built · runs per block

QA, then nine fix passes, then QA again

Each tile is opened headless and graded A–F on objects standing in the road, floating or buried buildings, terrain poking through asphalt, missing bridge decks, steps between tiles, and props inside walls. Then the fix passes run in a fixed order, each a script that changes one kind of thing:

  • street furniture and duplicates out of the carriageway
  • lane paint re-seated; building bases dropped to the ground on slopes
  • road surface smoothed; terrain carved under every street
  • poles off the road; old footprints hidden; gaps in the street network filled
  • level-aware smoothing so viaducts don't blend into the streets under them
  • bridge decks; floating towers grounded
  • parks pass and a physics tag for every object

Efficiency

  • Measure before trusting a fix. Every pass is judged by the score, not by intuition. One cross-slope re-fit looked right and passed the old checker, but the new surface checker showed it made tiles up to 30× worse, so it was removed from the chain.
  • Hide, never delete. Fixes hide objects and keep undo logs, so any repair can be reversed exactly.
  • Versioned cloud storage. Every upload keeps the previous version, so a whole block can be restored to a timestamp if a pass goes wrong.
04
Stage four

Surface sweep

Running daily

The green loop

Driving exposes what screenshots hide: a 4 cm step at a road seam, a sidewalk sitting under the road, a gutter flickering against the asphalt. The surface checker samples every road and sidewalk on a 0.5 m grid, scores each defect type, and the sweep tries the safe fixes tile by tile. A tile turns green when its completion score reaches 95%.

last 24 h: 575 improvements kept728 tiles props-cleaned

Efficiency

  • A gate on every change. A fix is kept only if the score improves and nothing else gets worse; otherwise the tile is left exactly as it was.
  • Re-run only when the fixes change. Each tile records a fingerprint of the fix scripts it last saw; a tile is reconsidered only when that set changes, so the sweep never repeats work.
  • Easiest wins first. The queue is ordered by how close a tile is to green, and tiles that can't reach green with the current fixes are skipped instead of retried.
  • Calibrated checker. 3,147 flagged spots on 28 tiles were checked against real features (driveways, crossings, speed bumps) so legitimate shapes aren't "fixed" away.
05
Stage five

Streets & lanes

Built · per block

Names, directions, signs

  1. Names matched between OpenStreetMap and the official street register, down to each block's house-number range.
  2. Lane graph: every road piece gets direction, lane count, turn rules, signals, PARE signs, bus lanes, speed bumps and cameras.
  3. Paint and signs: lane markings and the city's blue corner name plates, each showing its block's real number range.
159,063 travel lanes35,263 one-way pieces4,187 signalised crossings

Efficiency

  • One graph, many uses. The same lane graph draws the paint, places the signs, drives the AI traffic and the cars on this website's tile renders.
  • Only the new tiles. When a ring is built, the street pass runs on exactly those tiles, not the whole map.
06
Stage six

Props cleanup

Built

What it does

Every bin, pole, bench and tree is ray-tested. Anything inside a building, duplicated, or standing in the carriageway is moved to the nearest free spot on the sidewalk within 6 m, or hidden if there is none. The object grade must not get worse, and the surface must not get worse, or the tile is left alone.

728 tiles processed512 cleaned and uploaded

Efficiency

  • Fresh grades, not stale ones. A tile whose stored grade was out of date is re-graded and published even when nothing needed moving, so the map never lies about a tile.
  • Isolated scratch copies. Each run works in its own folder and compares against the cloud copy before uploading, so two machines can never overwrite each other's work.
07
Stage seven

Landmarks

Ongoing

Hand-built heroes

A few structures get unique models placed on top of the procedural tiles: MASP, the Ponte Estaiada, Estação da Luz, the Congonhas terminal and airfield, the Line 17 monorail. Next: Guarulhos airport, scoped from 302 taxiway sections, 52 jet bridges and three terminals in the map data.

Efficiency

  • Toolkits, not one-offs. The Congonhas airfield work (runway profiles, markings, lighting, stands) is a reusable toolkit, so Guarulhos starts most of the way there.
  • Audited by numbers. Each landmark has a scorecard (runways, markings, lighting, terminal, surroundings) measured before and after.
08
Stage eight

Ship

Running

From a finished tile to everywhere it's used

  1. Upload to versioned cloud storage, copy-only, and verify the uploaded file is identical before anything local is removed.
  2. Proxies for distant viewing and streaming.
  3. Website data: top-down renders, street lists, lane files and landmark pins feed this site's map and tile explorer.
  4. Live monitor: a local dashboard shows every machine's current task and every tile's state.

Efficiency

  • Offload as you go. A laptop disk can't hold a whole block (30–40 GB), so each tile is moved to the cloud a minute after it finishes and the local copy is freed only after a byte-for-byte check.
  • A job inbox in the bucket. Work is handed to cloud machines as small scripts dropped in shared storage; the machines pick them up, run them once and post results back. No machine needs to be reachable from outside.
  • Cache-busting for the site. Big images carry a version tag so visitors always get the current map without fighting caches.
09
Stage nine

Render & engine

Trailer rendering · Unity import ongoing

Film and game

  1. Film: a camera path is written as keyframes in world metres with heights above the real terrain, cut into shots; the renderer loads only the tiles each stretch of path can see.
  2. Engine: tiles are exported to Unity with a material-name contract, so the same procedural materials map to engine shaders.

Efficiency

  • Build the scene once per stretch. Loading the city for a single frame took ~25 s; rendering frames back to back in one session dropped it to ~7.6 s per 1080p frame.
  • Only what the camera sees. At most seven full-detail tiles near the camera; everything farther uses the light proxies.
  • Storyboard first. A one-frame-per-second preview of the whole cut costs a fraction of the real render and catches bad camera moves (a shot that flew into a rooftop, a landing aimed 19° off the runway) before money is spent.
  • The right processor for the job. City building runs on many CPU cores; rendering runs on a rented GPU, ten times faster per frame than CPU.
Machines & money

Three kinds of machine, one queue

The laptop

Builds tiles one at a time at low priority, runs the dashboards and relays jobs between the cloud and the scripts. A RAM guard and a disk guard keep it usable while it works.

free · always on

Cloud CPU workers

32- and 64-core machines rented on the spot market at about a third of the normal price. They can be reclaimed with two minutes' notice, so every job saves its progress to the bucket every few minutes and resumes where it stopped.

~67% cheaper than on-demand

A rented GPU

Rented by the hour only for rendering: one test frame first to measure the real cost, then the full job, then shut down.

cents per minute, only when needed
Rules that keep it safe

Copy, don't move

Uploads never delete anything in the cloud; old versions stay restorable.

Idle machines stop

Every cloud machine has a dead-man timer, so a forgotten machine can't keep billing.

Keep only what helps

Every automated change is scored before and after, and rolled back if it doesn't help.

One tile, one owner

Machines claim tiles and check the cloud copy before uploading, so parallel work never collides.
